    v2 status and roadmap

    Version 2.4.1 separates relational planning, grouping, and synchronous terminal helpers into dedicated modules. It preserves the public API, live callback bindings, source ownership, and fallback rules. The internal module map is in CONTRIBUTING.md.

    Version 2.4.0 adds stateful pipeline operations, composed collectors, shared execution limits, file recovery, and versioned report export. It also improves guarded Arrow execution and preserves conversion errors across optimized source paths. The completed research follow-up records the implementation scope and its local verification.

    Earlier release checkpoints and failed experiments below retain their original measurement dates, references, and limits.

    Version 2.3.0 adds batch mapping and caller-owned mapping executors, and fixes async callback type inference. It builds on 2.2.1's editor and planning fixes and 2.2.0's sorted operations, atomic file exports, correctness repairs, and execution reports.

    The 2.3.0 measurements use v2.2.1 as a separate release reference. Optimizations reduce setup cost for supported single-stage Python computed-column and projection queries. Sorted single-key grouping also avoids per-row wrapper allocation, and parallel maps can use a caller-owned executor. Single-collector grouping and further submission experiments remain candidates below. Some earlier correctness repairs increased execution costs, and their recorded regressions remain in the measurement history.

    Stability commitments

    Freeze public behavior

    Starting with 2.1, public names, signatures, exceptions, source-consumption rules, and engine fallback behavior remain compatible within the v2 release line. A documented safety limit may be tightened only with a changelog entry and an explicit opt-out. Other breaking changes belong in a future major release. v2 does not add an alias for every v1 method.

    Add native operations only with parity tests

    Add native operations only when they preserve Python ordering, equality, overflow, error, and cleanup semantics. Every new kernel needs Python/native parity tests and an explicit unsupported path.

    Keep spill behavior inspectable

    Keep spill diagnostics, partition selection, and resource limits visible for external sorts, joins, and grouped aggregation. Materializing operations should remain obvious in API documentation and plan explanations.

    Keep adapters current

    Keep Arrow as the preferred columnar interchange path and validate adapter behavior across supported pandas, PyArrow, and Polars releases. Third-party data packages remain optional dependencies.

    Included in 2.2

    These changes require version 2.2.0 or newer. See the changelog for the full list.

    • Sorted operations: Rows.group_by_sorted(), Flow.merge_sorted(), and bounded Rows.join_sorted() run in Python and validate consumed keys. They preserve encounter order and enforce the sorted join's row budgets.
    • File exports: Flow CSV/JSON/JSONL and Rows CSV/JSONL sinks offer optional atomic path output and no-overwrite publication after cleanup. Flow adds JSONL output for arbitrary values; Rows JSONL accepts a custom serializer. CSV header protection and stable relative output paths retain their documented defaults.
    • Errors and cleanup: uniqueness and grouping propagate user hash/equality errors. Arrow reports owned-resource close failures. Parquet's if_exists="error" publishes without overwriting a concurrent creator.
    • Live callbacks: grouping, pivot, projection, and computed columns preserve changes to selectors and collectors during consumption. File-scan projection rechecks selectors after custom openers. Exact builtin checks avoid invoking metaclass equality.
    • Scalar evaluation: caches retain constant types, arbitrary-size integers, object identity, and signed zero. Generated expressions share their location pass and reuse fixed fingerprint headers.
    • Guarded native execution: two-key integer count/sum grouping and retained list/tuple frequency continuation can use Rust. Unsupported inputs, changed functions, old extensions, and free-threaded execution keep their documented fallbacks. Keyed NumPy counting reads values between callbacks.
    • Reports: Pairs adds run_with_report() for its four eager terminals. Top-level record joins distinguish Rust, Arrow, and Python routes. Reports describe the outer query; they do not trace every stage.
    • Benchmark evidence: schema 6 records provenance, allocator settings, warmed blocks, and separate Python allocation measurements. Comparisons reject missing or mismatched evidence. CLI listing does not execute benchmark tasks.
    • Batch bounds: sync and async batching normalize integer bounds before consumption. CSV and SQLite retain conversion failures on the first record.
    • SQLite and ranges: SQLite destination names follow ASCII case rules and duplicate column aliases fail before inserts. Sync and async flows support exact counts and bounded reads of ranges longer than sys.maxsize.

    The browser playground runs a pure-Python wheel built from this checkout. Its status shows the package version, commit, working-tree state, and engine. Only a clean checkout matching the release tag is labelled a release build. See browser scope and execution reports.

Pathway has public BSL source, while Bodo has an Apache-2.0 core; neither belongs in an opaque-binary comparison by default. Compare an existing Arrow/NumPy pipeline with its first Python-row boundary, recording planning, reading, conversion and aggregation separately.     Execution controls and file recovery after 2.3.0

    The 2.4.0 work following the Kestra review also addresses data movement, shared executor pressure, and file-partition recovery. These are separate from execution reporting. Kestra's storage guidance and partitioned processing examples provided the design comparisons; fpstreams retains its existing lazy operators.

    BoundedExecutor supplies one unfinished-call budget to independent queries sharing a caller-owned pool. Each flow keeps its own result buffer and cleanup ownership. The wrapper leaves the underlying pool open. Saturated local probes use 3, 8, and 16 queries with the same worker and per-query buffer settings, recording aggregate pending calls and Python allocations separately from speed.

    FileCheckpoint.run() accepts a stable input file and a callback that writes one output file. It returns the verified output path, allowing subsequent stages to pass file references. Input bytes, resolved paths, and explicit processing versions identify partitions. Completed entries include output hashes; corrupt entries fail without silently replaying callbacks. This does not make external callback effects transactional or replay arbitrary iterators.

    The initial matching-schema Arrow path covered unchanged retained tables and record batches. Follow-up work also admits safe direct-field projections and primitive filters when the explicit schema matches their output, including metadata. Each batch is revalidated; changed column order or types, modified conversion hooks, and unsupported plans retain the row converter. Local probes cover narrow, wide, and nullable tables at 1,000, 10,000, and 100,000 rows, with unchanged-schema, inferred-schema, and cast controls measured separately.

    Three independent paired rounds with 21 samples each measured 98.4%–98.6% less time for direct projection and 94.7%–95.7% less for filtering plus projection at 100,000 rows. Controls stayed within 3%. Input preparation is outside timing; Python allocation peaks exclude prepared data and native heaps. These are local export-path measurements, not application speedups or a reviewed historical baseline. Zero-column Arrow and Polars output preserves row counts; Parquet writes reject nonempty rows without columns before publishing a destination.

    Bounded ranking and Python collector dispatch (2.4.0)

    agg.top(count, key=...) and agg.bottom(count, key=...) retain at most K whole items per state, keep equal keys in input order, and compose with existing global, async, hash, sorted, and spill aggregation. A heap entry is allocated only for a retained candidate. Keys run once per item, and payloads are never compared. The ranking recipe shows their use alongside a count.

    Three alternating local rounds at K=5 measured 92%–99% lower Python allocation peaks than collect-then-rank on 100,000 input records split into one or 60 groups. The bounded implementation took 13%–36% more time. At 1,000 records and 60 groups, its allocation peak was about 35% higher. Bounded state is useful for large groups; it is not a promise of lower latency or allocation for every shape. Avoiding temporary entries for discarded candidates reduced time by 35%–38% relative to the first bounded implementation at 100,000 records.

    Profiling six sums plus count and weighted metrics identified Python collector dispatch as a shared cost. Reusing the internal state lists within one row reduced time by 2.6%–4.5% and 2.2%–4.4%, respectively, at 100,000 dictionary records across three paired rounds. Mapping and unique-group controls remain separate; no application or unique-group speedup is claimed. Live collector getters, steps, completion checks, and finishers retain their order.

    Owned-record expansion helpers now live with record conversion. Rows retains the planning, snapshot, and materialized-path proofs; public interfaces remain unchanged apart from the two new aggregator factories.

    Further source comparisons

    Trino's pushdown documentation reinforces doing projection and filtering at the source. fpstreams already supports explicit Parquet scan projection/filtering and parameterized database queries with bounded fetches. Arbitrary Python callbacks still run in Python; moving them into a connector can change types, errors, and side effects.

    The 2.4.0 agg.min_by and agg.max_by select a whole record by a separate key. They cover batch latest-record selection and ranked records without collecting and sorting each group. Trino's keyed aggregations and Hudi's record-merging model supplied comparisons. fpstreams uses Python comparisons and keeps the first item on ties. It provides no persistent table, partial-update reconciliation, or event-time watermark. The versioned-record recipe applies deletion markers after selecting the winning version.

    Beam's accumulator lifecycle maps to existing collectors and reducers. Further partial aggregation needs explicit merge laws and measurements; arbitrary Python keys do not establish associativity. Changing when user callbacks run also requires preserving the v2 contract. ReactPHP streams and StreamSaver emphasize bounded transfer and sink completion, which fit existing buffered maps, owned source cleanup, and streaming file writers.

    Allegro's cache case study motivates measuring retained objects and lock contention. Current plan and kernel caches are bounded to 128 descriptors; their source-free, full-key lookup must remain intact. A Go-specific heap layout is not evidence for replacing these Python caches. StreamDiffusion offers batch and queue comparisons; similarity-based frame skipping is an application policy. Existing map_batches, filters, and shared executors provide explicit composition points.

    DBX, StreamPark, Java Stream, and IronMQ operate at database-client, job-platform, or message-delivery boundaries. Their useful comparisons are capability checks, recovery records, batching, and acknowledging work after success. Broker reservations and acknowledgments need a concrete connector contract before fpstreams can manage them. Functional-Light JavaScript, the FP jargon glossary, FunctionalPlus API search, and the Ironhack exercises inform naming and small examples. Existing pipe, curry, collectors, and the API index already provide those entry points. The awesome-bigdata list is a discovery index; each linked project's actual documentation and source remain the evidence for an implementation decision.

    Second source pass: composition boundaries

    Further reading of Beam's batch-size estimator and Trino's remaining-filter contract narrows the next work to existing composition boundaries.

    Parquet already has automatic projection and exact single-comparison scan hints, in addition to explicit source options. A synthetic 4,000-row, 20-column probe passed 10 rows and one column from the scanner to the executor for one range filter followed by a direct select. Adding a second range filter before the select retained correct output but passed all 4,000 rows and 20 columns. An explicit source-filter control passed 10 rows and one column. These are observed scanner outputs, not physical read counts or latency measurements.

    Version 2.4.0 carries the leading proven comparison through a longer guarded filter/projection prefix while retaining the original residual operations. It does not combine later filters: a later false predicate could remove a null row before an earlier comparison raises its Python TypeError. Unsafe batches reuse the lazy Python row-operation chain, preserving exception order and early exit. Parquet validates fallible source values before automatic hints discard them; explicit source options still define the visible input. This can require reading unused string, temporal, or nested columns. Repeated paired measurements compare the wider prefix against a baseline containing the same correctness fixes.

    The local comparison uses 1,000, 10,000, and 100,000 rows, narrow integer and wide mixed/nullable inputs, Parquet row output and retained Arrow batch output. Three alternating rounds contain 216 profiles with 21 samples each. At 100,000 rows, the two-filter projection takes 87.3%–88.3% less time for narrow Parquet and 80.2%–80.7% less for wide Parquet. Retained Arrow batch export takes 87.8%–88.2% and 92.2%–92.3% less time, respectively. Python allocation peaks fall by about 16% and 55% for Parquet, and 98%–99% for retained Arrow. The existing timing, allocation, and group gates pass; individual control time ratios range from 0.903 to 1.224 across all sizes and rounds.

    Preserving conversion errors has a separate cost. Against the earlier rules, the valid wide-text single-filter Parquet control takes 2.18–3.64 times as long because it validates values in columns and row groups that automatic hints previously discarded. Narrow integer controls remain near their earlier time. The next scan candidate is to read the required query columns and every field whose conversion can fail, retaining their original error order. These are local workload measurements; prepared inputs and native heaps are excluded from Python allocation, and physical I/O, RSS, and application timing were not measured.     Functional-programming source follow-up (2.4.0)

    The FP jargon glossary's unfold example motivates flow.unfold and aflow.unfold: a callback returns (value, next_state) or None to stop. fpstreams uses a lazy iterative source, permits None values inside a transition, and keeps callback-controlled termination explicit.

    map_accum(initial, function) provides stateful mapping over an existing source. Callbacks return (next_state, output), and the flow emits one output per consumed item.     Scope boundaries

    fpstreams is a local pipeline layer. It passes columnar and dataframe work to NumPy, pandas, Polars, or Arrow when appropriate and does not provide distributed execution. Unbounded inputs are not silently materialized.
