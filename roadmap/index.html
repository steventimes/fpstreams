    v2 status and roadmap

    Version 2.3.0 adds batch mapping and caller-owned mapping executors, and fixes async callback type inference. It builds on 2.2.1's editor and planning fixes and 2.2.0's sorted operations, atomic file exports, correctness repairs, and execution reports.

    The 2.3.0 measurements use v2.2.1 as a separate release reference. Optimizations reduce setup cost for supported single-stage Python computed-column and projection queries. Sorted single-key grouping also avoids per-row wrapper allocation, and parallel maps can use a caller-owned executor. Single-collector grouping and further submission experiments remain candidates below. Some earlier correctness repairs increased execution costs, and their recorded regressions remain in the measurement history.

    2.3.0 candidate checkpoint

    The local candidate verification on October 12 covered caller-owned mapping executors and explicit map_batches() on synchronous and asynchronous flows. Each batch produces one result; async callbacks keep the resolved return type, including mixed immediate and awaitable returns. Batch sizes, buffering, ordering, pool ownership, and cooperative cancellation remain explicit.

    The final Python source passed 4,307 tests with 10 skips and 88.05% branch coverage. Planning, native execution, spilling, and async execution passed their existing focus thresholds. All 211 Rust tests, lint, formatting, typing, version checks, and the offline dependency-lock check passed. Native and browser wheels and the source archive built successfully. Clean-install API checks passed on standard CPython 3.11 through 3.14. Installed-wheel checks also executed selected consumer code from the football, coursework, and data-quality projects using synthetic inputs; they establish compatibility, not application acceleration.

    Fresh measurements used CPython 3.12.13, CPU 2, one thread per numeric library, hash seed 0, release native builds, and the existing allocation tracing. The full integer/float engine matrix passed at 1,000, 10,000, and 100,000 items with 210 records per size. Three fresh processes per side and size, seven samples per process, and alternating invocation order supplied each comparison. All nine time/allocation checks passed against the prior development reference, and all nine passed in a separate comparison with released 2.2.1 Python source.

    The separate release comparison measured these reductions in median elapsed time:

    Query shape 1,000 rows 10,000 rows 100,000 rows
    Dict field with_columns() 32.9% 5.1% Within noise
    Mapping field with_columns() 14.4% Within noise Within noise
    Sorted grouping, integer/string/bytes key 19.5%–20.7% 19.9%–20.8% 18.2%–18.5%
    Sorted grouping, one tuple-valued key 11.9% 13.4% 12.7%

    These results describe local workloads and exclude import and input preparation. Mapping projection showed no measured benefit, and larger computed-column inputs did not establish a throughput gain. Tracked allocation peaks exclude prepared inputs and native heaps; they are not RSS measurements.

    Evidence is retained in the local artifacts/rc230-20261012/ directory. The final source/native fingerprints are 2665994d/916e3454, and the shared matrix is e464e9d0. The development reference is 7e9609bd/cc8bd052; the separate release reference is Python a6f8cdc8 with locally built release native cc8bd052. Those reports retain their original identities and are not merged into one baseline. Candidate validation does not publish the package or establish remote CI results.

    Included in 2.0

    • Domain-oriented package layout with small compatibility facades.
    • A primary synchronous Flow entry point, explicit relational Rows views, and lazy AsyncFlow and Pairs APIs.
    • Placeholder and row expression systems.
    • Collectors, named aggregators, and grouped aggregation.
    • Fused synchronous and asynchronous Python execution.
    • Native Rust scalar kernels and automatic Python/native planning.
    • Bounded concurrent async mapping, merge operations, timeouts, debounce, and time-windowed buffering.
    • CSV, JSONL, SQLite, DB-API, Arrow, Parquet, pandas, and Polars adapters.
    • External sorting and partitioned spill paths for joins and grouping.
    • One-shot source enforcement and cleanup of iterators, tasks, files, and connections owned by fpstreams.
    • Strict typing, Python/Rust parity tests, and wheel/sdist packaging.

    2.0 stabilization completed

    • Terminal-aware execution explanations and exact-size count routing.
    • Cached flat scalar-expression evaluators and linear native-prefix planning.
    • Single registries for synchronous and asynchronous operation dispatch.
    • Skew-aware spill repartitioning with finite partition, match, state, and output limits.
    • Spreadsheet-safe CSV as an opt-in mode and bounded JSONL records by default.
    • Patched development dependencies, SHA-pinned Actions, automated dependency updates, clean-install smoke tests for built wheels and the sdist, and SHA-256 manifests.
    • Machine-readable release benchmarks and branch-coverage gates for high-risk modules.

    • Record operations available from the primary flow() entry point, while preserving Rows as an explicit view and compatibility namespace.
    • Column and NumPy construction APIs, NumPy output, Rows concatenation, and standard Arrow C stream/dataframe protocol routing.
    • Structured execution reports for synchronous, asynchronous, and relational terminals.

    Stability commitments

    Freeze public behavior

    Starting with 2.1, public names, signatures, exceptions, source-consumption rules, and engine fallback behavior remain compatible within the v2 release line. A documented safety limit may be tightened only with a changelog entry and an explicit opt-out. Other breaking changes belong in a future major release. v2 does not add an alias for every v1 method.

    Add native operations only with parity tests

    Add native operations only when they preserve Python ordering, equality, overflow, error, and cleanup semantics. Every new kernel needs Python/native parity tests and an explicit unsupported path.

    Keep spill behavior inspectable

    Keep spill diagnostics, partition selection, and resource limits visible for external sorts, joins, and grouped aggregation. Materializing operations should remain obvious in API documentation and plan explanations.

    Keep adapters current

    Keep Arrow as the preferred columnar interchange path and validate adapter behavior across supported pandas, PyArrow, and Polars releases. Third-party data packages remain optional dependencies.

    Included in 2.2

    These changes require version 2.2.0 or newer. See the changelog for the full list.

    • Sorted operations: Rows.group_by_sorted(), Flow.merge_sorted(), and bounded Rows.join_sorted() run in Python and validate consumed keys. They preserve encounter order and enforce the sorted join's row budgets.
    • File exports: Flow CSV/JSON/JSONL and Rows CSV/JSONL sinks offer optional atomic path output and no-overwrite publication after cleanup. Flow adds JSONL output for arbitrary values; Rows JSONL accepts a custom serializer. CSV header protection and stable relative output paths retain their documented defaults.
    • Errors and cleanup: uniqueness and grouping propagate user hash/equality errors. Arrow reports owned-resource close failures. Parquet's if_exists="error" publishes without overwriting a concurrent creator.
    • Live callbacks: grouping, pivot, projection, and computed columns preserve changes to selectors and collectors during consumption. File-scan projection rechecks selectors after custom openers. Exact builtin checks avoid invoking metaclass equality.
    • Scalar evaluation: caches retain constant types, arbitrary-size integers, object identity, and signed zero. Generated expressions share their location pass and reuse fixed fingerprint headers.
    • Guarded native execution: two-key integer count/sum grouping and retained list/tuple frequency continuation can use Rust. Unsupported inputs, changed functions, old extensions, and free-threaded execution keep their documented fallbacks. Keyed NumPy counting reads values between callbacks.
    • Reports: Pairs adds run_with_report() for its four eager terminals. Top-level record joins distinguish Rust, Arrow, and Python routes. Reports describe the outer query; they do not trace every stage.
    • Benchmark evidence: schema 6 records provenance, allocator settings, warmed blocks, and separate Python allocation measurements. Comparisons reject missing or mismatched evidence. CLI listing does not execute benchmark tasks.
    • Batch bounds: sync and async batching normalize integer bounds before consumption. CSV and SQLite retain conversion failures on the first record.
    • SQLite and ranges: SQLite destination names follow ASCII case rules and duplicate column aliases fail before inserts. Sync and async flows support exact counts and bounded reads of ranges longer than sys.maxsize.

    The browser playground runs a pure-Python wheel built from this checkout. Its status shows the package version, commit, working-tree state, and engine. Only a clean checkout matching the release tag is labelled a release build. See browser scope and execution reports.

    2.2.1 preparation and verification

    The completed 2.2.1 preparation round used released 2.2.0 source as its local benchmark reference. It covered 1,000, 10,000, and 100,000 inputs, plus callback mutation, bounded streaming, and async backpressure experiments. Raw reports and the diagnostic profiles of that 2.2.0 source are kept in artifacts/next-version-review-20261007/. These measurements do not create a CI historical baseline.

    The released-source reference exposed failures in the existing same-run limits for 1,000-item automatic list and tuple sums. The two larger input sizes passed, and the 100,000-item holdout passed comparison with three reference runs.

    A follow-up using saved and optimized 2.2.1 source reduced the median time for those small sums by 8.8% for lists and 7.7% for tuples. Each side used three runs with seven samples per scenario. The optimized auto/Python ratios were 1.05–1.07, within the original 1.1 limit. All nine timing and allocation comparisons at 1,000, 10,000, and 100,000 inputs passed. Tracked peak allocation was unchanged for these sums. Raw reports, including failed intermediate candidates, are in artifacts/auto-sum-optimization-20261007/; this remains local evidence rather than a CI historical baseline.

    The released commit passed 4,217 Python tests with 10 skips, the branch-coverage gates, and 211 Rust tests. Release builds produced eight native wheels and one sdist; their hashes match the GitHub attachments, SHA-256 manifest, and PyPI files. CPython 3.11–3.14 installations from PyPI passed native, Python, async, and missing-extra smoke checks. This packaging evidence is separate from the local performance measurements. Local publication records are in artifacts/release-2.2.1-20261007/.

    Computed-column setup after 2.2.1

    Fresh comparisons used released 2.2.1 source as the reference. Both sides ran on CPython 3.12.13 with the same release native extension, CPU 2 affinity, single thread settings, hash seed, and default allocator settings. Each side had three independent process runs at each size, with seven samples per implementation.

    The matrix now has 16 computed-column cases, including dict and MappingProxyType inputs, five- and 32-column records, explicit Python controls, and a NumPy control. Five projection cases ran alongside them. All nine timing and tracked-allocation comparisons passed the existing regression limits. Verified aggregates from that selection are retained; its original temporary report files are unavailable. A fresh retained selection of the three dict selector cases also passed all nine comparisons. The table below uses those retained reports.

    For supported single-stage queries, execution now binds each query's callback and fallback to a shared loop template. This removes repeated AST construction and compilation. The original enrichment function still copies each row before reading its live selector list against the original input. Multi-stage loops use the existing compiler.

    Analytics feedback and the next feature scope

    The soccer analytics usage report supplied prepared-list team aggregation, generator-fed cohort counts, and weighted player metrics as concrete workloads. The benchmark now includes those input shapes, and Mapping projection controls use the same prepared Mapping rows on both sides. Small first-query costs and warmed throughput are recorded separately; normalization, deduplication, sorting, and database reads retain their own costs.

    The current sorted single-key candidate reduced complete-consumption time by 18%–20% for integer keys, 18%–20% for string/bytes keys, and 11%–13% for tuple-valued keys across 1,000, 10,000, and 100,000 prepared rows. All nine time/allocation comparisons passed. Merge and join controls stayed within about 1%. This result concerns explicitly sorted grouping, not the report's ordinary hash groups. See sorted measurements.

    Caller-owned executors provide explicit pool reuse while preserving query-owned cancellation and cleanup. A small synthetic spawn diagnostic separated startup, first output, submission, computation, and shutdown; it supports checking startup cost separately, without establishing a general batching or application speedup. The existing chunk().map_parallel().flat_map() composition remains available. The new analytics recipes use existing v2 interfaces.

    The final source passed 4,288 Python tests with 10 skips and all branch-coverage, lint, formatting, and strict-type gates. Each of the three engine matrices contained 210 passing records. Installed wheel checks passed on standard CPython 3.11–3.14, and the browser wheel and strict documentation build passed. A local consumer check called the application's actual team, player-weighted, and cohort functions with synthetic inputs through saved release, preceding development, and current wheels. All three agreed with the application's Python reference; application source and the supplied report were unchanged. This is functional compatibility evidence, not a full application run or speed claim. Records are retained in artifacts/next-api-feedback-20261011/.

    Consumer feedback and engine references reviewed on October 12

    Two additional consumer reports narrow the next experiments. The COSI116 consumer used installed 2.2.1 for a read-only SQLite query, six numeric sums plus a count, and a validated one-to-one adjacent-season join. Its saved 32,574-row/60-group and 10,670-pair results agree with independent references; the report contains no formal performance comparison. A quality-worker report uses pinned 2.1.0 with a file iterator and one stateful reduce callback. Its Decimal checks, deadlines and original-row evidence require sequential callback semantics. These are consumer reports, not acceptance of this development tree.

    The proprietary references are Photon and the separately licensed q core behind PyKX. Pathway has public BSL source, while Bodo has an Apache-2.0 core; neither belongs in an opaque-binary comparison by default. REA inspected the official PyKX 4.1.0 wheel's archive and public wrapper API. The recorded package digest matches PyPI. Native engine algorithms and vendor runtime performance were not established by that inspection.

    Photon's published architecture motivates measuring conversion boundaries before adding kernels. Compare an existing Arrow/NumPy pipeline with its first Python-row boundary, recording planning, reading, conversion and aggregation separately. Preserve a supported columnar segment where safe; one-shot sources must keep their streaming fallback. PyKX's null-conversion documentation also shows why skipping validation can change the values a user receives. Compare nullable and null-free numeric inputs with the original semantics.

    The next profiles should cover multiple collectors and generic stateful reduce before revisiting the existing single-collector path. Use prepared dict/Mapping records, fresh generators, and filtered SQLite inputs as separate workloads. Retain strict join cardinality, empty-input behavior, callback errors, source cleanup, and the original-row evidence order. A cheap integer-reduce probe alone cannot establish a bottleneck in a Decimal-based worker.

    Current run_with_report("reduce", function, initial) already observes a reduce terminal. Investigate optional, bounded stage/transition diagnostics only when the outer report leaves a concrete profiling question unanswered. Consumption counts and cancellation accounting would need their own definitions; they are not existing report fields. Keep ordinary execution free of mandatory per-row instrumentation and source replay. These are proposed experiments, not measured fpstreams improvements or new release APIs.

    Next development steps

    Start each further candidate from the verified development source after the measured changes above. Use released v2.2.1 for a separate comparison of the combined changes. Build a release extension for each side and collect fresh reports with the same harness, interpreter, dependencies, runtime settings, input shapes, and invocation order. Reproduce any cost suggested by older profiles on the chosen reference before changing code. Verify FPSTREAMS_BENCHMARK_SOURCE and the imported source fingerprint when selecting the reference checkout.

    Start row comparisons at 1,000, 10,000, and 100,000 items with the existing rows.with_columns*, rows.select*, rows.group_sum.python.*, and sorted.* competitive cases. Include callable/Python controls and inspect the observed route before attributing a gain to the Python loop. For small planning changes, also check short inputs and either side of the existing native crossover.

    Each candidate needs a fresh profile, a correctness-checked reference, one implementation change, and repeated timing/allocation comparisons. Add negative regressions to the closest existing test module and then run the complete Python checks for an execution change. Extend the matrix before measurement when a required shape is missing, and regenerate both sides after any matrix change. Keep a candidate only when it beats run-to-run noise and passes the existing gates. Preserve failures and revert neutral candidates.

    Single-collector grouping already has a dedicated execution path. Profile that path before changing it; do not add another implementation. The soccer report's team and weighted summaries use multiple collectors, so their measured cost cannot establish a single-collector bottleneck.

    The earlier COSI107 assignment comparison using pre-change and optimized 2.2.1 wheels took about 168.48 and 168.00 seconds in one run each, with equal outputs. That establishes application compatibility, not an application speedup. Process experiments must separate submission cost, startup, callback computation, first-result latency, and final cleanup. Begin with the existing explicit chunk(...).map_parallel(...).flat_map(...) composition. Batch size changes the unit of buffering and can change callback/error timing; compare those semantics when evaluating a new batching option or executor reuse. Deferred sources keep their reopening behavior, and the process backend keeps spawn.

    There is no reviewed benchmarks/baselines/engine-v2.json in this checkout. The scheduled workflow's median of three same-checkout runs checks consistency within a revision. A historical baseline needs review in its target CI runner; local reports cannot establish that result.

    Additional diagnostics, bounded statistics, and extension hooks remain candidates without a release date. Free-threaded CPython 3.14t stays experimental and non-blocking; standard CPython 3.11–3.14 is the supported release matrix.

    Compatible fixes and internal performance changes are maintenance candidates. The caller-owned executor and explicit map_batches() additions ship in 2.3.0. Batch mapping uses the existing chunk and map paths, produces one result per batch, and supports sync pool defaults or async map controls. Replay interfaces remain proposals; reduce_by() already covers per-key state reduction. Dependency updates also get their own lock, adapter, and platform validation; they are reviewed separately from performance changes. The stable release is 2.3.0. The local candidate results above retain their original measurement dates and scope.

    The map-based projection, executor-forwarding removal, Counter(map(...)), frozen-field inlining, and shared Mapping-check shortcuts remain rejected. Their failed callback, lifetime, or timing cases are regression requirements for future work.

    Scope boundaries

    fpstreams is a local pipeline layer. It passes columnar and dataframe work to NumPy, pandas, Polars, or Arrow when appropriate and does not provide distributed execution. Unbounded inputs are not silently materialized.

    Repository validation

    CI checks source changes. Before building release artifacts, the publish workflow also validates the tag, rebuilds the native extension, and runs the complete Python and Rust test suites on Linux. Together, the repository workflows provide:

    • Python/native parity tests for supported plan families;
    • tests, lint, strict typing, Rust formatting, clippy, and package builds;
    • contract tests for one-shot sources, cancellation, spilling, and fallbacks;
    • clean-install and native/Python smoke tests for every wheel and the sdist;
    • source tests on standard CPython 3.11 through 3.14, with the separate CPython 3.14t job remaining experimental and non-blocking;
    • repository and focus-module branch-coverage thresholds;
    • SHA-pinned CI actions, OIDC-based PyPI publishing, and SHA-256 artifact manifests;
    • a documented migration path for supported v1 entry-point aliases.
